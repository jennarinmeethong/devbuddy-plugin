# สคริปต์พรีเซนต์ DevBuddy × REAL

**เวลาพูด:** เนื้อหาหลักสไลด์ 1–14 ประมาณ 10–11 นาที · ภาคผนวกสไลด์ 15–20 เปิดตามคำถาม (ภาพ BMS สี่หน้าใช้เพิ่มประมาณ 2 นาที)

**แกนเรื่อง:** คนรับงานต้องรู้ว่าอะไรยืนยันแล้ว อะไรอาจเก่า และอะไรยังต้องถาม → เสนอวิธีเก็บและค้นความรู้ → ทดลองวัดเวลาและคุณภาพ

**แยกให้ชัดตลอดการพูด:** ภาพ BMS ในภาคผนวกแสดงหน้าจอของระบบที่ deploy แล้ว ส่วนวิธีนำระบบไปแก้ pain และเกณฑ์วัด REAL เป็นแนวทางทดลอง ยังไม่มีผลวัดว่าประหยัดเวลาได้จริง เคสคืนเงินในสไลด์ 4 เป็นสถานการณ์สมมติ ไม่ใช่ข้อมูล BMS

## สไลด์ 1 — เปิดเรื่อง (25 วินาที)

“ลองนึกถึงวันที่เรารับงานต่อจากทีมเดิม มีเอกสารให้ แต่ยังตอบไม่ได้ว่าเรื่องไหนเป็นข้อสรุปล่าสุด วันนี้ผมจะเสนอวิธีใช้ DevBuddy เก็บความรู้ตั้งแต่เริ่มโปรเจกต์จนถึงวันส่งต่อ และเสนอวิธีทดลองวัดผล ตัวเลขเวลาที่จะเห็นเป็นเป้าหมายกับตัวอย่างคำนวณ ยังไม่ใช่ผลที่วัดได้จริง”

**ส่งต่อ:** “ก่อนดูเครื่องมือ ขอเริ่มจากปัญหาที่คนรับงานเจอ”

## สไลด์ 2 — Pain ที่เกิดกับคนรับงาน (45 วินาที)

“ปัญหามีสามชั้น ชั้นแรก เราได้รับ docs หรือ KT แต่คนเพิ่งเข้ามายังไม่รู้บริบท ไม่รู้ว่าข้อมูลครบหรือเป็นปัจจุบัน จึงต้องไล่หาเอง ชั้นที่สอง บางเคสไม่เคยคุยกัน หรือคุยแล้วไม่ได้บันทึก กฎธุรกิจสำคัญจึงตกหล่นหรือถูกจำผิด ชั้นที่สาม พอเจอ issue หรือ edge case ระหว่างทำงาน ก็ต้องกลับไปถาม SA, BA หรือ module owner อีกครั้ง ปัญหาไม่ใช่การถามผู้รู้ แต่คือเราแยกไม่ออกว่าอะไรยืนยันแล้ว และอะไรยังต้องถาม”

**ส่งต่อ:** “เมื่อคำตอบของรอบนี้ไม่ถูกเก็บ คนถัดไปก็จะเจอสามช่วงเดิม”

## สไลด์ 3 — วงจรที่ทำให้ถามซ้ำ (35 วินาที)

“อ่านภาพจากซ้ายไปขวา: เรารับเอกสารมา แล้วสืบต่อจากเอกสาร โค้ด และคนที่เคยทำ เพราะยังไม่แน่ใจว่าข้อมูลใหม่แค่ไหน พอเจอช่องว่างทางธุรกิจ ก็ถามผู้รู้ การถามผู้รู้ยังจำเป็น โดยเฉพาะเรื่องที่มีผลต่อกฎธุรกิจ แต่ถ้าคำตอบไม่มีที่มาและไม่ถูกเก็บกลับเข้าระบบ คนถัดไปต้องเริ่มสืบและถามใหม่ สิ่งที่อยากลดจึงเป็นเวลาตรวจความใหม่ เวลาสืบช่องว่าง และคำถามที่ถามซ้ำ”

**ส่งต่อ:** “ขอยกสถานการณ์หนึ่งให้เห็นว่าช่องว่างนี้หน้าตาอย่างไร”

## สไลด์ 4 — สถานการณ์สมมติ (45 วินาที)

“สมมติมีคนรับช่วงงานแก้ flow ยกเลิกคำสั่งซื้อหลังชำระเงิน เขาได้เอกสารและ KT เดิม แต่ไม่แน่ใจว่ากฎคืนเงินยังใช้เหมือนเดิมหรือไม่ คำถามที่ต้องหาคำตอบคือ ‘กรณีนี้คืนเงินแบบไหน และใครยืนยัน’ เคสสมมตินี้ยังไม่มีคำตอบธุรกิจ เพราะ BA หรือ owner ต้องเป็นคนยืนยัน สิ่งที่อยากให้เครื่องมือช่วยคือหาข้อสรุปเดิมพร้อมที่มา ชี้เรื่องที่ยังไม่รู้ เตรียมคำถามให้ตรงจุด แล้วเก็บคำตอบที่ยืนยันแล้วไว้ให้คนถัดไป”

**ส่งต่อ:** “เคสนี้เป็นงานรับช่วง แต่ความรู้ไม่ควรรอให้ถึงวันส่งต่อจึงค่อยเริ่มเก็บ”

## สไลด์ 5 — โปรเจกต์ใหม่กับงานรับช่วง (40 วินาที)

“สไลด์นี้มีสองทางเข้า ถ้าเป็นโปรเจกต์ใหม่ เราเริ่มเก็บขอบเขต กฎธุรกิจ decision ข้อสันนิษฐาน และเจ้าของเรื่องตั้งแต่ kickoff ถ้าเป็นโปรเจกต์ที่ส่งต่อ เราเริ่มจาก docs กับ KT แล้วเทียบกับสิ่งที่กำลังทำ ตรวจ revision และจดช่องว่างที่ต้องถาม ทั้งสองทางควรเข้าสู่ฐานความรู้ของโปรเจกต์เดียวกัน โดยแยกข้อสรุปที่ยืนยันแล้วออกจากคำถามที่ยังเปิดอยู่”

**ส่งต่อ:** “ต่อไปคือวิธีที่เสนอให้ DevBuddy และ AI ช่วยกัน โดยยังให้คนเป็นผู้ตัดสินเรื่องธุรกิจ”

## สไลด์ 6 — แนวทาง solution (45 วินาที)

“ดูจากซ้ายไปขวา ข้อมูลเริ่มต้นอาจมาจาก kickoff หรือ docs กับ KT ที่รับต่อมา เราผูกข้อมูลกับงาน แหล่งที่มา ฉบับแก้ไข และคำถามค้างไว้ใน DevBuddy จากนั้น plugin ให้ AI ช่วยค้นสิ่งที่มีอยู่ วิเคราะห์จุดที่ยังไม่ชัด และร่างคำถามเฉพาะเรื่อง เช่น เอกสารสองฉบับขัดกันตรงไหน SA, BA หรือ module owner ยืนยันความหมายทางธุรกิจ ส่วน Reviewer ตรวจบันทึกก่อนเผยแพร่ คำตอบที่ยืนยันแล้วจึงกลับมาเป็นบริบทของคนถัดไป”

**ส่งต่อ:** “ถ้าถามว่าใครใส่อะไรเข้าไป และได้อะไรกลับมา สไลด์ถัดไปแยกเป็นสองเส้นทาง”

## สไลด์ 7 — Input / Output สองกลุ่มผู้ใช้ (60 วินาที)

“แถวแรกคือคนนำเข้าความรู้ Input เป็นงาน เอกสาร KT หลักฐาน และคำยืนยันที่ได้รับ เขาตรวจที่มา ระบุสิ่งที่ยังไม่ชัด แล้วสร้าง Draft Output ขั้นนี้คือร่างที่มีฉบับแก้ไขและที่มา อาจมีคำถามค้าง แต่ยังไม่ใช่ความรู้ที่เผยแพร่ ตรงกลางคือคนตรวจ: Reviewer อ่านฉบับนั้น ถ้าหลักฐานยังไม่พอจะส่งกลับพร้อมเหตุผล ถ้าผ่านจึงอนุมัติ แล้วกด Publish เป็นอีกขั้น

แถวล่างคือคนค้น Input เป็นคำถามและ project ที่ตัวเองมีสิทธิ์ เขาค้นผ่านเว็บ หรือถาม AI ผ่าน plugin กับ MCP Output คือรายการบันทึกที่ Published พร้อมที่มาและฉบับแก้ไขให้เปิดตรวจต่อได้ ถ้าค้นไม่พบ ก็บอกว่าไม่พบในขอบเขตที่ค้น แล้วค่อยให้คนหรือ AI ช่วยระบุคำถามที่ต้องยืนยัน จุดเชื่อมของสองแถวคือ Draft ที่ผ่านคนและเผยแพร่แล้ว กลายเป็นความรู้ให้คนถัดไปค้นใช้”

**ส่งต่อ:** “คนกับ AI เข้าถึงความรู้ชุดนี้จากคนละช่องทางอย่างไร”

## สไลด์ 8 — เส้นทางค้นของคนและ AI (45 วินาที)

“แถวบนคือคนในทีมค้นผ่านเว็บ ระบบตรวจสิทธิ์ใน project ก่อนให้เปิดบันทึกที่เผยแพร่และดูที่มา แถวล่างคือผู้ใช้ถาม AI ใน Claude, Codex หรือ Cowork ผ่าน plugin และ MCP ซึ่งตรวจตัวตน สิทธิ์ และนโยบาย AI ในทุกคำขอ ทั้งสองทางอ้างอิงบันทึกที่เผยแพร่ชุดเดียวกัน AI ช่วยสรุปพร้อมอ้างอิง แต่ผู้ใช้ยังเปิดดูต้นฉบับได้ และถ้ายังไม่มีคำตอบที่ยืนยันแล้ว ต้องบอกตามนั้น ในเคสคืนเงินสมมติ จึงส่งคำถามให้ BA แทนที่จะให้ AI เดากฎธุรกิจ”

**ส่งต่อ:** “แล้วคำตอบใหม่ที่ BA ยืนยันจะเข้าฐานความรู้อย่างไร”

## สไลด์ 9 — จาก Draft ถึง Published (55 วินาที)

“ไล่ตามลูกศร Contributor หรือ AI ช่วยสร้าง Draft โดยผูกกับงานและแหล่งที่มา AI ทำได้ถึงขั้นร่าง คนรับผิดชอบอ่านและส่งตรวจ จากนั้น Reviewer ตรวจเนื้อหา หลักฐาน และฉบับที่กำลังจะอนุมัติ ตรงนี้มีสองทาง: ถ้าผ่านจึงอนุมัติ แล้วกด Publish แยกอีกขั้น; ถ้ายังไม่ผ่าน Reviewer ส่งกลับพร้อมเหตุผล บันทึกกลับเป็น Draft ผู้ร่างแก้เป็นฉบับใหม่และส่งตรวจอีกครั้ง ทางย้อนกลับนี้สำคัญ เพราะความรู้ที่คนถัดไปใช้อ้างอิงต้องเป็นฉบับที่ Published แล้วเท่านั้น”

**ส่งต่อ:** “workflow นี้ไม่ใช่หน้าที่ของคนคนเดียว ลองดูว่า BA, Dev และ QA เข้ามาตรงไหน”

## สไลด์ 10 — งานของแต่ละ role (50 วินาที)

“BA อ่าน requirement และกฎธุรกิจเดิม เพื่อชี้จุดที่ไม่ชัดหรือขัดกัน Dev เทียบเอกสารกับโค้ดและพฤติกรรมปัจจุบัน แล้วระบุ edge case หรือผลกระทบ QA เทียบ acceptance กับหลักฐานการทดสอบ เพื่อหากรณีที่ยังไม่ครอบคลุม ส่วน SA, BA หรือ module owner ที่รู้เรื่องนั้นยืนยันความหมายทางธุรกิจ ในเคสคืนเงินสมมติ BA ยืนยันกฎ Dev ระบุจุดที่ flow ต้องเปลี่ยน QA เตรียมกรณีทดสอบ แล้วทีมจึงบันทึกข้อสรุปพร้อมที่มา ผู้รู้เรื่องกับ Reviewer ในระบบอาจเป็นคนเดียวกันหรือคนละคน ขึ้นอยู่กับสิทธิ์ใน project”

**ส่งต่อ:** “ถ้าจะบอกว่าวิธีนี้ตอบโจทย์ REAL ต้องมีหลักฐานแบบไหน”

## สไลด์ 11 — REAL เป็นเกณฑ์พิสูจน์ (45 วินาที)

“R หรือ Real Use คือมีหลักฐานว่าใช้กับงานจริง ทั้งโปรเจกต์ใหม่และงานรับช่วง ไม่ใช่แค่ทดลองหน้าจอ E หรือ Efficiency Gain คือวัดเวลาที่ใช้หาบริบท ตรวจความใหม่ และเตรียมคำถาม A หรือ Always-On คือดูว่าทีมบันทึก decision และคำยืนยันระหว่างทำงานหรือก่อนปิด task ใช้เวลาจากคำยืนยันถึงการบันทึกนานเท่าไร L หรือ Leverage คือมีคนหรืองานถัดไปนำบันทึกที่ยืนยันแล้วกลับมาใช้จริง เราควรรายงานโปรเจกต์ใหม่กับงานรับช่วงแยกกัน เพราะจุดเริ่มและเวลาฐานต่างกัน”

**ส่งต่อ:** “มิติที่กรรมการมักถามต่อคือ E: เราจะประเมินเวลาอย่างไรให้เชื่อได้”

## สไลด์ 12 — วิธีประเมินเวลา (60 วินาที)

“เริ่มจากนิยามงานที่เทียบกันได้ และกำหนดจุดเริ่มกับจุดสิ้นสุดให้เหมือนกัน เช่น เริ่มเมื่อผู้รับงานลงมือหาบริบท จบเมื่อมีข้อมูลพอเริ่มทำหรือส่งคำถามที่มีที่มา จากนั้นจับเวลาลงมือทำสามช่วง: หาข้อมูล ตรวจความใหม่กับช่องว่าง และเตรียมคำถามหรือสรุป รวมเวลาแก้ผลจาก AI และเวลาคนตรวจ Draft ด้วย ส่วนเวลารอ BA หรือ owner ตอบให้เก็บแยก เพื่อเห็นว่าเวลาลดลงที่ขั้นตอนไหนจริง

เมื่อมี baseline และ pilot ที่งานใกล้เคียงกัน จึงเทียบค่ามัธยฐานต่อ task ภายในกลุ่มเดียวกัน พร้อมบอกจำนวนงานและระดับความยาก ตัวอย่าง 120 นาทีเหลือ 80 นาที คิดเป็นลดประมาณ 33 เปอร์เซ็นต์ ตัวเลขนี้มีไว้แสดงสูตร ยังไม่ได้วัดผลจริง และต้องดูคุณภาพหลักฐาน จำนวนครั้งที่แก้ และการถามซ้ำควบคู่กัน”

**ส่งต่อ:** “วิธีวัดนี้นำไปสู่ pilot ขนาดเล็กที่ตัดสินใจต่อได้”

## สไลด์ 13 — Pilot ที่เสนอ (40 วินาที)

“ข้อเสนอคือเลือกงานโปรเจกต์ใหม่หนึ่งกลุ่ม และงานรับช่วงอีกหนึ่งกลุ่ม สัปดาห์แรกเก็บ baseline แยกกัน สัปดาห์ที่สองถึงสามทดลองใช้ โดยบันทึกเวลา คำถามที่ต้องยืนยัน จำนวนครั้งที่แก้ Draft และการนำบันทึกเดิมไปใช้ สัปดาห์ที่สี่สรุป R, E, A และ L แยกสองกลุ่ม พร้อมตรวจว่าคุณภาพคำตอบลดลงหรือไม่ เป้าลดเวลาลงมือทำอย่างน้อย 30 เปอร์เซ็นต์เป็นเกณฑ์ทดลอง ไม่ใช่ผลที่รับประกัน”

**ส่งต่อ:** “สิ่งที่อยากขอให้ตัดสินใจวันนี้จึงเป็นการทดลอง ไม่ใช่การรับรองผลล่วงหน้า”

## สไลด์ 14 — ปิดเรื่อง (30 วินาที)

“ข้อเสนอคือเริ่มเก็บความรู้ตั้งแต่วันแรก เพื่อให้วันที่มีคนรับงานต่อไม่ต้องเริ่มจากศูนย์ ลองใช้กับทั้งโปรเจกต์ใหม่และงานส่งต่อ แล้วตัดสินจากสามอย่างร่วมกัน: เวลา คุณภาพคำตอบ และการใช้ความรู้ซ้ำ ถ้าเรื่องใดยังไม่ชัด ให้ระบุช่องว่างและส่งให้ผู้รู้ยืนยัน นี่คือจุดที่ DevBuddy ควรช่วยทีมได้ สไลด์หลักจบตรงนี้ ภาคผนวกมีโครงระบบ สิทธิ์ และภาพตัวอย่างจากเว็บไว้ตอบคำถาม”

## ภาคผนวก A · สไลด์ 15 — โครงสร้างระบบ (เปิดเมื่อถามว่ามีอะไรบ้าง)

“ภาพนี้เป็นองค์ประกอบของ DevBuddy ที่จะนำมาใช้ในแนวทางทดลอง เว็บเป็นช่องทางของคนสำหรับจัดการ project ค้น ตรวจ และอนุมัติ ส่วน plugin และคำแนะนำของแต่ละเครื่องมือช่วยให้ AI ค้น วิเคราะห์ และร่าง ทั้งสองทางใช้แกนข้อมูลเดียวกันผ่าน API หรือ MCP ที่ตรวจสิทธิ์ ข้อมูลหลักคืองาน บันทึก ข้อสรุป ที่มา และฉบับแก้ไข ส่วนระบบค้นหา ประวัติการกระทำ และนโยบายการเข้าถึงช่วยให้ตรวจสอบได้ ถ้าถามเรื่อง vector database ให้ตอบสั้น ๆ ว่าเป็นดัชนีเสริมสำหรับค้นตามความหมายเมื่อเปิดใช้งานและมีข้อมูลในดัชนี ข้อมูลหลักยังอยู่ในบันทึก และการค้นข้อความยังใช้ได้”

## ภาคผนวก B · สไลด์ 16 — สิทธิ์ (เปิดเมื่อถามว่าใครทำอะไรได้)

“Viewer ค้นและอ่าน Contributor วิเคราะห์และสร้าง Draft Reviewer ตรวจ อนุมัติ และเผยแพร่ Administrator จัดการสมาชิก ขอบเขต project และนโยบาย AI ส่วน IndexMaintainer เป็นสิทธิ์เฉพาะของงานตรวจบันทึกที่อาจล้าสมัย งานสร้างดัชนีค้นตามความหมายใช้บัญชี Viewer แยกต่างหาก ลูกศรในภาพคือการส่งต่องาน ไม่ใช่ลำดับชั้นของสิทธิ์ AI เข้าถึงได้เฉพาะ project ที่เปิด AI access และผู้ใช้มีสิทธิ์อยู่แล้ว”

## ภาคผนวก C · สไลด์ 17–20 — ภาพ BMS ที่ปิดข้อมูลแล้ว (เปิดเมื่อถามหา UI จริง)

**พูดก่อนเปิดภาพ:** “สี่ภาพต่อไปเป็นภาพประกอบจากเว็บที่ deploy เราปิดข้อมูลบัญชี รหัสงาน ชื่อบันทึก คำค้น และเนื้อหาภายในแล้ว ภาพผ่านการแก้ไข จึงใช้ดูโครงหน้าจอและขั้นตอน ไม่ใช้ยืนยันถ้อยคำทุกจุดในระบบจริง”

**สไลด์ 17 · ขอบเขตโปรเจกต์ (25 วินาที):** “ภาพนี้แสดง BMS และโปรเจกต์ที่เกี่ยวข้องใน workspace เดียวกัน ก่อนบันทึกหรือค้น เราต้องเลือก project ให้ถูก เพราะความรู้และสิทธิ์ผูกกับขอบเขตนั้น”

**สไลด์ 18 · บริบทงาน (30 วินาที):** “เมื่อเปิดงาน จะเห็นบันทึกที่เกี่ยวข้องและสถานะต่างกัน นี่เป็นจุดเริ่มให้คนรับช่วงไล่ดูบริบท พร้อมแยกได้ว่าเรื่องใดเป็น Draft เรื่องใดอนุมัติแล้ว และเรื่องใด Published ส่วนเวลาที่ลดได้จากการใช้งานลักษณะนี้ต้องวัดใน pilot”

**สไลด์ 19 · บันทึกที่ Published (25 วินาที):** “ภาพนี้แสดงสถานะและส่วนประวัติของบันทึก ประเด็นที่อยากให้เห็นคือคำตอบควรย้อนดูที่มา วันที่ และข้อจำกัดได้ ไม่ใช่มีแค่ข้อความสรุป ชื่อและเนื้อหาจริงถูกปิดไว้”

**สไลด์ 20 · การค้น Input → Output (30 วินาที):** “Input ของผู้ค้นคือ project คำค้น และตัวกรอง Published ส่วน output คือรายการบันทึกพร้อมสถานะให้เปิดตรวจต่อได้ ภาพตัวอย่างนี้มีผลจากการค้นข้อความ แต่ช่องค้นตามความหมายยังไม่คืนผล จึงไม่ใช้เป็นหลักฐานว่าดัชนี semantic พร้อมใช้งานใน BMS”

## ประโยคสั้นสำหรับคำถามที่น่าจะเจอ

- **“AI ตอบเองได้เลยไหม?”** “ให้ AI ช่วยค้น สรุปพร้อมที่มา และร่างคำถามได้ เรื่องที่ยังไม่มีข้อสรุปต้องให้ผู้รู้ยืนยัน และการเผยแพร่ต้องผ่านคน”
- **“Input กับ output คืออะไร?”** “ฝั่งบันทึกใส่งาน เอกสาร หลักฐาน และคำยืนยัน ได้ Draft ที่มีที่มา แล้วคนตรวจและเผยแพร่; ฝั่งค้นใส่คำถามกับ project ได้รายการบันทึกที่เปิดตรวจต่อ หรือผลว่าไม่พบในขอบเขตที่ค้น”
- **“ทำไมต้องมี vector database?”** “ใช้เป็นดัชนีเสริมเพื่อค้นตามความหมายเมื่อเปิดใช้และมีข้อมูลในดัชนี ข้อมูลหลักยังอยู่ในบันทึก ส่วนการค้นข้อความยังใช้ได้”
- **“ประหยัดเวลากี่เปอร์เซ็นต์?”** “ยังไม่มีผล pilot ตัวเลข 30 เปอร์เซ็นต์เป็นเกณฑ์ที่เสนอ และตัวอย่าง 120 เหลือ 80 นาทีมีไว้แสดงสูตร เราจะวัดกับงานชนิดเดียวกันและดูคุณภาพควบคู่”
