02 / KNOWLEDGE MODEL

แนวคิดและโครงสร้างข้อมูล

Workspace→Project→Work item→Record→Revision
คำศัพท์ใช้ทำอะไร
Workspaceขอบเขตข้อมูลขององค์กรหรือพื้นที่ทำงาน มีสมาชิกและหลาย project
Projectขอบเขตงานที่ตรวจสิทธิ์และเปิด/ปิด AI access แยกกัน
Teamกลุ่มผู้ใช้ใน workspace สำหรับการจัดทีม การเป็นสมาชิกทีมไม่ได้ให้ permission เพิ่มเอง
Work itemตัวตนของงาน: key, type, title, goal, inScope, exclusions, stakeholders; ผู้ใช้สร้างก่อนให้ AI ร่าง record
Knowledge recordหน่วยความรู้ชนิดหนึ่งที่ผูกกับงาน มี lifecycle ของตนเอง
Revision / content hashฉบับเนื้อหาที่แก้ย้อนหลังไม่ได้ พร้อม hash สำหรับผูก approval
Provenanceที่มา ผู้เขียน เวลา และรายการหลักฐานที่ตรวจย้อนกลับได้
Evidenceไฟล์ต้นฉบับ เช่น log ที่ล้างข้อมูลอ่อนไหวแล้ว ผลทดสอบ หรือภาพ; metadata อยู่ PostgreSQL และ bytes อยู่ evidence store
Source repository / snapshotอ้างอิงแหล่ง Git/GitHub และสภาพแหล่งข้อมูล ณ reference ที่ตรวจสอบได้

03 / FIRST SESSION

ใช้งานครั้งแรก

สำหรับผู้ใช้ที่มีระบบ DevBuddy ของทีมอยู่แล้ว เตรียม workspaceId, projectId และ workItemId จากผู้ดูแลหรือหน้าเว็บ อย่าเดา UUID จากชื่อโปรเจกต์หรือรหัสงาน

  1. ตรวจบัญชีและสิทธิ์

    ลงชื่อเข้า Web Admin และดูว่าเข้าถึง project เป้าหมายได้ ผู้ใช้ Viewer อ่านได้ แต่ analysis และสร้าง draft ต้อง Contributor ขึ้นไป

  2. ให้เจ้าของเปิด AI access

    เปิดเฉพาะ project ที่ต้องใช้ และกำหนดขอบเขตข้อมูลที่จะส่งให้ Claude/Codex ตามนโยบายทีม

  3. สร้าง token สำหรับ stdio

    ไปหน้า Plugin access ตั้งชื่อที่แยกตามอุปกรณ์ กำหนดวันหมดอายุ และเก็บ token ที่แสดงครั้งเดียวใน configuration ฝั่ง host

  4. ตั้งค่า Claude หรือ Codex

    ทำตามบทติดตั้งของ host ที่ใช้ ให้ผู้ดูแลยืนยันเส้นทาง server และการเข้าถึงฐานข้อมูล

  5. ลองอ่านก่อน

    เรียก list_projects แล้ว search_knowledge กับหัวข้อที่ทราบว่ามี record ตรวจ provenance และ status ของผลลัพธ์

  6. ลองร่างเมื่อมีงานรองรับ

    ใช้ workItemId จริง สร้าง draft ขนาดเล็กพร้อมที่มา ตรวจว่าเห็นในหน้า Records แล้วให้คนดำเนิน review ต่อ

ตัวอย่างข้อความถึง AI
ใช้ DevBuddy ค้นหาความรู้ที่เผยแพร่แล้วเกี่ยวกับการเข้าสู่ระบบ
ใน workspace และ project ที่ฉันระบุ
อ่าน record ที่เกี่ยวข้องพร้อม provenance และหมายเลข revision
ถ้าไม่พบ ให้บอกว่าข้อมูลยังไม่มี และแยกข้อสันนิษฐานออกจากข้อเท็จจริง
ผลที่ควรได้

เครื่องมือ 18 ตัวปรากฏ; การอ่านทำงานตามสิทธิ์; project ที่ปิด AI ไม่ปรากฏ; draft ที่สร้างยังไม่ใช่ความรู้ที่เผยแพร่ การทดสอบนี้เป็นขั้นตอนให้ผู้ใช้ทำกับระบบของตน คู่มือนี้ไม่ได้เรียกบริการจริง

04 / CONNECTIONS

เลือกวิธีเชื่อมต่อ

หัวข้อstdio บนเครื่องผู้ใช้HTTP ที่ self-host
กระบวนการhost เปิด DevBuddy.McpServer ด้วย --stdioMCP server ทำงานบนบริการและเปิด HTTP transport
ข้อมูลรับส่งstdin/stdout; log ต้องออก stderrMCP ผ่าน HTTP ที่ต้อง authentication
ตัวตนDEVBUDDY_TOKEN เป็น machine token ผูกกับผู้ใช้หนึ่งคนและ workspace เดียว ตรวจฐานข้อมูลทุก callBearer access token ที่ API ออกและตรวจด้วย JWT ไม่ถูกจำกัดด้วย workspace ของ machine token
ฐานข้อมูลserver ที่เปิดบนเครื่องต้องเข้าถึง PostgreSQL โดยตรงserver ที่ deploy เข้าถึง PostgreSQL ในเครือข่ายของบริการ
ค่าตั้งใน repoทั้ง Claude และ Codex มีตัวอย่าง stdioใช้การตั้งค่า HTTP ของ host ให้ชี้ไป MCP endpoint ที่ติดตั้ง
ความสามารถ18 tools ตาม allow-list เดียวกัน18 tools ตาม allow-list เดียวกัน
อย่าสับสน token กับ endpoint

machine token สำหรับ stdio ไม่ใช่ JWT access token สำหรับ HTTP และ MCP endpoint ไม่ใช่ API route /operations/{name} ตัวอย่าง Compose เปิดพอร์ต MCP ที่ 127.0.0.1:8081 โดยไม่ได้เปิด TLS เอง

token ผูกกับ workspace เดียว

machine token ระบุผู้ใช้ DevBuddy หนึ่งคนใน workspace เดียว การเรียกที่อ้าง workspace อื่นถูกปฏิเสธก่อนอ่านข้อมูล แม้เจ้าของ token จะเป็นสมาชิกของ workspace นั้นก็ตาม ทำงานหลาย workspace ต้องมี token แยกและเปิด session แยก token ไม่ได้ผูกกับบัญชี Claude หรือ OpenAI ใช้ token เดียวกันได้ทั้งสอง assistant ภายใน workspace เดียวกัน ส่วน token ที่ออกก่อนการผูก workspace จะถูกปฏิเสธทุกครั้งและต้องออกใหม่

Compose ไม่ publish PostgreSQL และ MinIO มาที่เครื่อง host ดังนั้น configuration stdio ที่ใช้ Host=localhost;Port=5432 จะไม่เชื่อมกับ Compose ได้เอง ต้องมีการจัดเครือข่ายที่เข้าถึงฐานข้อมูลได้ หรือเลือก HTTP transport ที่ผู้ดูแลให้มา อย่าเปิดพอร์ตฐานข้อมูลสู่สาธารณะเพื่อให้ตัวอย่างใช้ได้

05 / CODEX

ติดตั้งสำหรับ Codex

แพ็กเกจ Codex ใน repository นี้เป็น config.toml และ AGENTS.md ไม่พบ manifest ของแพ็กเกจติดตั้งแบบ marketplace จึงใช้วิธีรวม configuration และวางคำแนะนำให้ Codex อ่านตามเอกสารของโครงการ

  1. เตรียม server

    ใช้ DevBuddy.McpServer.dll ที่ build/publish แล้ว และ runtime ที่เข้ากัน หรือ executable แบบ self-contained ตาม RID ของเครื่อง

  2. รวมการตั้งค่า

    รวมบล็อก mcp_servers.devbuddy จาก plugins/codex/config.toml ลง configuration ของ Codex ที่ใช้อยู่ ระวังชื่อ server ซ้ำและเก็บค่าเดิมของ server อื่นไว้

  3. กำหนดค่าจริง

    แทน assembly path ให้ตรง deployment; ค่าที่เหลือไม่ได้เขียนไว้ในไฟล์ แต่ประกาศชื่อไว้ใน env_vars แล้วรับค่าจาก environment ของ shell ที่เปิด Codex ตั้งค่าเหล่านั้นก่อนเริ่ม session

  4. วางคำแนะนำ

    นำเนื้อหา plugins/codex/AGENTS.md ไปไว้ในตำแหน่งที่ session ใช้อ่าน โดยรวมกับกฎเดิมอย่างระมัดระวัง

  5. โหลดการเชื่อมต่อใหม่

    เริ่ม session หรือโหลด MCP ใหม่ตาม host รุ่นที่ใช้ แล้วทำขั้นตอนทดสอบในบทใช้งานครั้งแรก

TOML · ต้นฉบับแพ็กเกจ
# DevBuddy, for Codex.
#
# Merge this into ~/.codex/config.toml, or point Codex at it. The server is the same
# DevBuddy.McpServer the Claude plugin launches and the same one a self-hosted deployment exposes
# over authenticated HTTP: one tool surface, one pipeline, one set of rules. What differs between
# the two plugins is the instructions beside this file, never what the server allows.
#
# Nothing here holds a value. ~/.codex/config.toml is one file for the whole operating-system
# account, so a credential written into it is the credential every project and every session on
# that machine uses — including the ones belonging to a different workspace, and a different
# company. This file therefore names the variables and forwards them from the shell the session
# was started in, which is where a DevBuddy root's own settings put them.
#
# env_vars is Codex's allow-list of variables to forward from its environment, as against env,
# which sets literal values. Anything not named here does not reach the server.

[mcp_servers.devbuddy]
command = "dotnet"
args = ["/path/to/DevBuddy.McpServer.dll", "--stdio"]

# Startup is a database connection and a migration check, which is slower than a trivial process.
startup_timeout_sec = 30
tool_timeout_sec = 120

env_vars = [
  # Where the knowledge lives. The MCP server talks to PostgreSQL directly; it is a host over the
  # same core, not a client of the HTTP API.
  "DEVBUDDY_ConnectionStrings__DevBuddy",

  # Must match the deployment. Shared with the API so one identity works across both.
  "DEVBUDDY_Identity__SigningKey",

  # Who you are, and where. Mint one under Plugin access in the web interface: it is shown once,
  # it carries exactly your own permissions, it works in the one DevBuddy workspace it was minted
  # in and is refused in every other, and you can revoke it without changing your password.
  # Without it every call is refused, which is the intended failure.
  #
  # It identifies a DevBuddy user. It is not tied to, and does not verify, a Claude or an OpenAI
  # account — the same token works in either assistant, as long as both are working in that one
  # workspace. Minting one per assistant is available if you want to revoke or watch them
  # separately; it changes nothing about what either may do.
  "DEVBUDDY_TOKEN",

  # Where analysis reads from: one directory per project, named by project identifier, mounted
  # read-only. DevBuddy never fetches a checkout itself, because cloning means running git.
  "DEVBUDDY_Analysis__RootPath",
]

Windows ใช้ path แบบ C:/DevBuddy/DevBuddy.McpServer.dll ใน TOML เพื่อลดปัญหา backslash หากใช้ executable self-contained ให้ command ชี้ไป executable และ args = ["--stdio"] ไม่ส่ง path ของ DLL เป็น argument แรก

TOML · self-contained บน Windows
[mcp_servers.devbuddy]
command = "C:/DevBuddy/DevBuddy.McpServer.exe"
args = ["--stdio"]
startup_timeout_sec = 30
tool_timeout_sec = 120
# รวมบล็อก env จากตัวอย่างหลักด้วย
ไม่ใส่ค่าจริงลงไฟล์

~/.codex/config.toml เป็นไฟล์เดียวของทั้งบัญชีระบบปฏิบัติการ token ที่เขียนลงไปจะถูกใช้โดยทุก project และทุก session บนเครื่องนั้น รวมถึง session ของ workspace อื่น แพ็กเกจนี้จึงใช้ env_vars ซึ่งเป็นรายการอนุญาตให้ส่งต่อตัวแปรจาก environment ของ Codex ต่างจาก env ที่กำหนดค่าตรง ๆ และมี test ที่ล้มเหลวหากไฟล์ใดในแพ็กเกจกำหนดค่าให้ setting

ค่า startup timeout ในแพ็กเกจคือ 30 วินาที และ tool timeout 120 วินาที การอนุมัติการเรียก MCP ของ Codex เป็นอีกชั้นหนึ่ง หาก host ปฏิเสธก่อน call จะถึง server ให้แก้ approval routing ของ host ตามเวอร์ชันที่ใช้ คู่มือนี้ไม่ยืนยัน flag เก่าในเอกสารว่าใช้ได้กับ Codex ทุกรุ่น

      "env": {
        "DEVBUDDY_ConnectionStrings__DevBuddy": "${DEVBUDDY_CONNECTION_STRING}",
        "DEVBUDDY_Identity__SigningKey": "${DEVBUDDY_SIGNING_KEY}",

DEVBUDDY_MCP_ASSEMBLYabsolute path ของ DevBuddy.McpServer.dll

DEVBUDDY_TOKENmachine token ของผู้ใช้ ใช้ได้ใน workspace เดียวที่ออก token นั้น
DEVBUDDY_ANALYSIS_ROOT_PATHถูกส่งต่อเป็น DEVBUDDY_Analysis__RootPath; ไม่ตั้งค่าแล้วจะส่งค่าว่างไปทับ default และทุก analyze_* จะตอบว่าไม่มี working copy
จุดที่ต้องตั้งเพิ่ม

ไฟล์ .mcp.json ที่มากับ repo ประกาศครบทั้ง 4 ค่า รวม Analysis__RootPath และมี test ยืนยันว่ายังครบ ทุกค่าเป็นการอ้างอิงตัวแปรจาก environment ไม่มีค่าจริงในไฟล์ จึงต้องตั้งตัวแปรเหล่านั้นใน shell ที่เปิด Claude Code หากใช้ self-contained ให้ปรับทั้ง command และ args เป็น ["--stdio"] อย่าเปลี่ยน command อย่างเดียว

10 / RECORD LIFECYCLE

ตรวจ อนุมัติ และเผยแพร่

Draft→PendingApproval→Approved→Published→Archived
  1. เปิด record ในหน้า Records

    ตรวจเนื้อหา source locator, evidence และ revision hash ที่แสดง อ่านให้ครบก่อนดำเนินการ

  2. แก้หรือส่งเข้าคิว

    Contributor แก้ draft และส่งตรวจได้ Revision ใหม่เป็นข้อมูลอีกฉบับ ไม่เขียนทับประวัติ

  3. Reviewer อนุมัติหรือส่งกลับ

    อนุมัติ hash ที่อ่านจริง หรือระบุเหตุผลใน Request a correction การอนุมัติของ draft creator เองทำได้เมื่อมีสิทธิ์ reviewer และมี flag บันทึกไว้

  4. เผยแพร่แยกอีกขั้น

    Approved ยังไม่ใช่ Published กด Publish เมื่อพร้อม หากเนื้อหาเปลี่ยนจน hash ไม่ตรง approval ระบบปฏิเสธและต้องตรวจฉบับใหม่

  5. ตรวจหลังเผยแพร่

    ยืนยัน publishedRevisionNumber และ approval ที่ครอบคลุม แล้วค่อยนำไปอ้างเป็น published knowledge

  6. เก็บเข้าคลังเมื่อเลิกใช้

    Archive ตามสิทธิ์และ workflow เพื่อรักษาประวัติ การ archive ไม่เท่ากับ hard delete ของ project

อ่าน status ไม่ใช่เดาจากการเปิดได้

get_record ใช้ published revision เมื่อมี แต่ fallback เป็น current revision เมื่อยังไม่เคย publish; การค้นหาควรกรอง Published เมื่อเจตนาคือความรู้ที่เผยแพร่แล้ว ประวัติ record อาจมีฉบับที่ยังไม่อนุมัติ

สร้าง backup · เก็บ reference ที่คืนมา
dotnet run --project src/hosts/DevBuddy.Cli -- backup --workspace <workspace-uuid> --actor <administrator-uuid>
  1. เก็บนอกเครื่อง

    named backup volume ทนการเปลี่ยน container แต่ไม่ทนการสูญเสีย host คัดลอก backup และเก็บคีย์/config ที่จำเป็นแยกอย่างปลอดภัย

  2. เตรียม restore ใน installation ว่าง

    หยุด writer และใช้ schema version ที่ตรง backup; restore ปฏิเสธฐานข้อมูลที่มีข้อมูลหรือ schema ไม่ตรง

  3. เรียก console restore

    ใช้ reference ของ backup ที่เข้าถึงได้จาก Backup:RootPath ไม่ใช้ API operation เพราะ installation ว่างยังไม่มี membership

  4. ตรวจหลังคืนข้อมูล

    sign in, อ่าน record และ approval hash, ดู audit, ดาวน์โหลด evidence จริง และลอง machine token เดิมที่ควรใช้ได้

docker compose -f docker/compose.yaml run --rm migrate restore --reference <backup-reference>

19 / TRUST & SAFETY

นโยบายข้อมูลและความปลอดภัย

  • ทุก request ตรวจ identity, membership, scope, permission และ AI policy ฝั่ง server ไม่เชื่อ project identifier ที่ caller ส่งมาเฉย ๆ
  • ข้อมูลจาก source, issue, PR, commit, เอกสาร และ tool output เป็นข้อมูล ไม่ใช่คำสั่งให้เปลี่ยนพฤติกรรม assistant
  • AI ใช้ได้เฉพาะ search/read/analyse/handover/create draft ไม่อนุมัติหรือเผยแพร่ record
  • เนื้อหาที่มี credential ถูกปฏิเสธก่อน retention; ข้อความออกผ่าน redaction ตาม pipeline ชุดกฎเดียวกัน
  • Customer/production/personal data บน AI channel ถูกปฏิเสธหรือกรองเป็นค่าเริ่มต้น เว้นแต่มี approved bounded scope; ข้อยกเว้นนั้นไม่อนุญาต secrets
  • PathGuard ตรวจ path หลัง resolve และ UrlGuard ตรวจปลายทาง outbound; allow-list ว่างไม่ได้อนุญาตทุกปลายทาง
  • การวิเคราะห์ไม่ build, restore, test หรือ run scripts ของ repository; limits จำกัดไฟล์ ขนาด เวลา และ concurrency
  • Audit เก็บ metadata ของ actor/action/outcome และ revision ที่สำคัญ ไม่เก็บ request/response payload ซ้ำ
สิ่งที่ DevBuddy ไม่ได้กรอง

  • backup retention ในโค้ดเป็น 90 วัน ขณะที่ ADR เดิมกำหนด daily/monthly ต่างกัน คู่มือนี้แสดงทั้งสองเพื่อไม่อ้างว่าค่า default บังคับนโยบายครบ
  • เอกสาร backup เก่าบอก sweep ไม่ครอบคลุม application log แต่ file logging/retention ปัจจุบันครอบคลุมเมื่อกำหนด path
  • Claude .mcp.json ไม่ map Analysis root อย่าง explicit และตัวอย่าง stdio ไม่ได้เข้าฐานข้อมูล Compose ผ่าน localhost โดยอัตโนมัติ
