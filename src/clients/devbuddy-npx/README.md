# DevBuddy npm client — development preview

Stage A passed on 2026-10-25. The approved full client plan is now being implemented:
`devbuddy-npx` provides registry/token commands, the header helper and stdio bridge, sharing
schema 1 and credentials with .NET. `private: true` deliberately prevents publication before
production platform, host and release acceptance. Existing plugin defaults and the .NET client
remain unchanged. See [the setup/rollback guide](../../../../docs/operations/npm-client.md),
[contract acceptance checklist](../../../../docs/npx-client-contract.md) and
[ADR-0016](../../../../docs/adr/0016-node-client-feasibility.md).

The production package exposes only `devbuddy-npx`. `devbuddy-credential-probe` remains a separate
private feasibility artifact generated by `tools/prepare-feasibility.mjs`; native evidence below
is historical prototype evidence, not acceptance of the new production client.

## What is implemented

- A strict TypeScript/ESM prototype, compiled for Node.js 24; Bun builds and runs unit tests.
- Pinned Koffi 3.3.3, loaded only when the native store is needed.
- Direct Credential Manager and Keychain adapters using the same keys and UTF-8 values as .NET.
- A synthetic round-trip probe and an opt-in .NET/Node interoperability runner.
- Native file hashes, Windows signatures, SAC state and Code Integrity evidence collection.
- Source guard tests for execution APIs, nonliteral imports and unapproved native library loads.

The Linux-compatible file store, checkout registry, CLI and MCP helper/bridge now have local
contract tests. `node dist/main.js --help` runs the client; `node tools/client-smoke.mjs` tests
real Node HTTP/stdio with isolated synthetic credentials; `node tools/package-smoke.mjs` checks
the production inventory, script-disabled installation and installed entrypoint. The latter's
readonly smoke works even with the native dependency entrypoint unavailable. Cross-platform
production and real-host checks are still pending. No package is published.

## Separate feasibility tarball through npx

After building, run from this directory in PowerShell:

```powershell
./tools/npx-smoke.ps1 -Native
```

This packs the prototype, checks the file inventory, and runs it through `npx` from a clean folder
whose path includes Thai characters. It uses a new workspace-local npm cache, tests cold and warm
invocations, disables all install scripts, and verifies that the native module comes from the
isolated cache rather than the source checkout. No global installation or publication occurs.
Omit `-Native` for help-only launcher checks, as CI does. Evidence is retained under ignored
`out/npx-smoke-<UUID>` folders. A successful run is local-artifact evidence, not a published-client
or independent SAC-policy check.

The smoke test also rejects an invalid stage and an invalid probe UUID through the packed npx
entrypoint, requiring exit 1, empty stdout and a safe stderr message that does not echo the
synthetic sensitive argument. These negative cases run without accessing a credential store.
The owner reconfirmed the original gate on 2026-10-25: additional prototype tests only; the full
CLI/MCP port must wait for the remaining native/platform evidence.

## Build and unit tests

From this directory, with Node.js 24 and Bun installed:

```powershell
bun install --frozen-lockfile --ignore-scripts
bun run typecheck
bun run build
bun test tests
node dist/probe-main.js --help
```

TypeScript 5.9.3 is intentional: the source guard uses its stable compiler AST API. Runtime code
uses no compiler API. The Node process, not Bun's FFI compatibility, is the native test target.

## Native round trip

Run in an interactive user session on Windows x64/ARM64 or macOS:

```powershell
node dist/probe-main.js roundtrip
```

The probe creates one random `devbuddy:test/npx/<UUID>` item, reads, updates and deletes it, and
checks missing-item behavior. It uses public synthetic strings, never a user's real token.
Cleanup runs in `finally`; after a forcibly terminated process a test item can remain. It can be
removed with `node dist/probe-main.js cleanup <UUID>` or from the OS credential interface.
The `read-dotnet` and `verify-node` stages are reserved for the compatibility runner.

No process is launched by `src/`. Test tools under `tools/` may launch Node and .NET with separate
argument arrays and `shell: false`. The probe never changes SAC, registry policy or Keychain access
settings. It does not silently switch to file storage if native access is refused.

## Read and write across .NET and Node

Build the existing client tests first, from the repository root:

```powershell
dotnet test tests/DevBuddy.Client.Tests -c Release
```

Then from this directory:

```powershell
node tools/compatibility.mjs
```

The runner uses a random test key to check .NET write → Node read/update → .NET read/update →
Node read. It asks the existing .NET adapter to remove the item in `finally`, including when the
Node adapter cannot load. Each subprocess has a two-minute limit. An interrupted runner may leave
its isolated synthetic item. The ordinary .NET suite does not activate the opt-in exchange unless
`DEVBUDDY_NPX_PROBE_ID` is set; a normal passing suite is not interoperability evidence.

For remote machines without the complete xUnit suite, a dependency-free peer compiles the
unchanged production credential adapter source instead:

```powershell
dotnet build tools/npx-feasibility/CredentialPeer -c Release
# From src/clients/devbuddy-npx:
node tools/compatibility.mjs ../../../tools/npx-feasibility/CredentialPeer/bin/Release/net10.0/CredentialPeer.dll
```

This source-linked peer is test tooling, not a replacement client. The local Windows exchange
passed with it. Remote preparation helpers under `tools/npx-feasibility` install checksum-verified
official Node 24 and SDK 10.0.400 into `~/.devbuddy-npx-test`, use Bun 1.3.14, and leave system PATH
and runtime installations unchanged. The Unix helper uses existing curl or wget without sudo.

## Windows/SAC evidence

In PowerShell from this directory, after building the .NET peer above:

```powershell
./tools/windows-evidence.ps1 -IncludeCompatibility
```

The ignored `out/windows-feasibility` directory receives JSON reports and bounded diagnostics.
The collector records the installed `.node` files even if SAC prevents loading, plus native files
actually loaded by a successful probe. Inspect `environment.json` for signatures and SAC state
before/after. State `0` means off, `1` enforcement, `2` evaluation. Missing event-log access is
recorded rather than represented as an absence of blocks. Reports may include local file paths;
review before sharing. Nothing is uploaded.

Repeat on a Windows x64 and ARM64 system already running SAC in enforcement, using an up-to-date
Node.js 24 security patch. Do not change security policy to make the test pass. Even a successful
prototype is not a released-package SAC claim: the later packed and published client needs its own
end-to-end drills.
